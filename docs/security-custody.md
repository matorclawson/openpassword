# Security operations

**Human owner, trusted browser, no sudo.** Use the configured HTTPS console origin. For a local trial use localhost. A numeric IP may work for ordinary vault access while a browser rejects it as a passkey relying party.

## Read permission and agent use

Jane unlocks a two-secret private vault, opens **Human read access**, and gives Joe her recipient card through a channel where he can independently verify her identity. The card includes the workspace, profile and full SHA-256 public-key fingerprint. Joe opens the item, pastes the card, selects the duration and grants read access. Jane can list shares and explicitly reveal the item. An edit or replacement ends further delivery of that revision. Joe can revoke under **List shared items**. Rotate the actual provider credential when a previous reader should lose the ability to use a value already copied.

For a named team, use **Human read access → Read groups**. Verify each recipient card, one per line. A group accepts up to 16 named people. Granting a revision publishes every recipient envelope atomically. A roster edit withdraws all copies delivered through that group and requires explicit sharing of the current revision with the new roster. A separate individual grant survives a group change.

For an agent, Joe selects **Delegate to gateway** and authorizes its separate copy. He then grants only the intended operations and time window. Human read sharing and gateway delegation have separate controls. Rotating or removing a human share does not rotate a credential held by a gateway.

## Sign-in and device unlock

In **Workspace → My profile → Sign-in passkeys**, enter the current account password and name a passkey. Register a second authenticator if desired. A social-only account must first add a local password. The account can now sign in with a passkey. The vault still requires its unlock factors or an explicitly configured recovery/device path. After enrollment, operations such as adding a host, granting access or creating a readable share prompt for user verification. Removing the final passkey returns the account to its prior session-based policy. A stolen session before first enrollment is a separate threat. Enroll from a trusted session.

In an unlocked two-secret vault, **Recovery and device unlock** offers an optional thirty-day enrollment. Re-enter the vault factors and use a user-verifying authenticator with device-bound PRF support. Backup-eligible authenticators are refused for this flow. From another signed-in, unlocked browser use **Manage enrolled devices → Revoke device**. The official client checks the enrollment before its next device unlock. The thirty-day expiry and revocation are enforced by the official client, not by cryptography: a modified or offline client holding the device's wrapped key and authenticator is not stopped by them. An enrollment abandoned part way can remain listed; revoke it. Losing every factor and every recovery method loses access.

## Recovery rehearsal

**Owner and optional designated custodian, their respective trusted browsers, no sudo.** Under **Recovery and device unlock** the owner can create a file and offline code. Save each separately. For assisted recovery, verify the custodian's recipient card independently and select **Create custodian-assisted kit**. Keep the recovery file under the owner's or organization's chosen custody. Send only the custodian envelope to the custodian. Their unlocked vault opens that envelope. After independently verifying the requester, they return the code privately. The owner signs into the original origin and uses **Other ways to unlock** with the file and code. Rehearse this procedure on a second device. Possession of both parts is permanent recovery authority over matching snapshots. This is explicit single-custodian assistance, without an organization-wide master key. Operator-held encrypted backups remain separate.

## Separate model gateway

**Custodian administrator, independently managed host, ordinary console account, no sudo.** Install this candidate on the credential-holding deployment. Create a model connection and an expiring model grant for its chat operation alone. Specify the exact model, maximum requests, maximum output tokens and any applicable budget. Send just the short-lived access token privately to the routing administrator. Keep the refresh token and provider secret with the custodian. **Prerequisite: the custodian workspace must be a standalone workspace.** A deployed broker makes every new workspace host-required and refuses an unbound access token there, and the router attaches no host proof, so this mode does not work with a newly installed custodian. It works only with a workspace that already had grants when host approval was introduced and has not enrolled a host. Anyone holding the downstream token can spend its remaining allowance. A call that disconnects after dispatch may have been charged upstream. This release supports unbound downstream access tokens. Its ordinary access-token lifetime is at most fifteen minutes.

**Routing deployment administrator, service configuration on the routing host, normal service-management privileges.** Set OPENPASSWORD_MODEL_CUSTODIAN_ORIGIN to the custodian's exact HTTPS origin and restart the broker. In the console create a **Separate OpenPassword gateway (scoped access token)** connection using the downstream access token. Issue a separate router grant with its own limits. A change of custodian origin requires creating a new connection. Rotate expired tokens through the usual connection rotation. The router does not refresh the downstream token. A refusal after dispatch is reported as an uncertain outcome; reconcile using the custodian's usage ledger. Operator configuration is trusted. Separate administrators, release authority and machines are necessary for meaningful compromise isolation.

**Broker operator, service configuration on either host.** For wrapped-master deployments set OPENPASSWORD_REQUIRE_WRAPPED_MASTER=1 together with OPENPASSWORD_WRAPPING_KEY_FILE. Follow the existing offline wrapping procedure before enabling it on a plain-key installation. The guard refuses startup without the configured external file. The running broker can still use the master key.

## Independent verification

Use synthetic credentials. Verify new-device login, a denied passkey, a changed request after approval, attempted replay, revoked shares, recovered vault contents and device loss. Restore both old and new vault snapshots on Linux ARM64 using the operator's test backup key. Exercise a physical authenticator on each supported browser. Verify both deployments' ingress, trust roots and logs. Have independent reviewers examine browser-delivery compromise, recipient-key substitution, recovery-file custody and broker compromise before publishing production security claims.
